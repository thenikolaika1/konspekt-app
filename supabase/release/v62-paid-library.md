## Бюджет: как считается резерв

- O — сколько успешных генераций ещё осталось у всех действующих и будущих (продлённых заранее) сроков Premium.
- Резерв Premium R = ceil(O × k), k = 1,5 (запас на неудачи и повторы: неудачная генерация лимит ученика не тратит, а общий бюджет тратит).
- Твой резерв — 10 запусков за 30 дней (для проверки работы).
- Свободно = (бюджет − израсходовано) − R − твой оставшийся резерв.
- Пробный период и запуски без Premium проходят, только если после запуска остаётся не меньше R (+ твоего резерва — для учеников).
  Ученик с Premium запускается всегда, пока есть общий бюджет и его лимит.
- Новая выдача или продление Premium в панели проверяет, что свободно ≥ ceil(10 × 1,5) = 15. Иначе — «Бюджета ИИ не хватает».
- Бюджет нельзя поставить меньше «израсходовано + R».
- **k = 1,5 — оценка, а не гарантия.** При большом числе технических сбоев GigaChat бюджет может кончиться раньше — тогда его увеличиваешь ты.
- Ничего не меняется автоматически: `max_in_flight = 1`, модели и бюджет — как были. Новый бюджет задаёшь ты (шаг 6).

**Сейчас в production бюджет 40, израсходовано 10:** осталось 30, твой резерв 10 → свободно 20 → можно продать только
**1** Premium (нужно 15). Пробные генерации встанут на паузу, когда останется ≤ 10. Поэтому до первых продаж
увеличь бюджет (шаг 6).

Пример: бюджет 300, израсходовано 120, у 3 учеников с Premium осталось 10 + 7 + 4 = 21 генерация →
R = ceil(21 × 1,5) = 32; свободно = 180 − 32 − 10 = 138 → можно продать ещё 9 Premium.

**Шаг 0в. Генеральная репетиция на своём компьютере** (не production; рекомендуется перед шагом 1). Нужен локальный
PostgreSQL 17 на **127.0.0.1:55432** и **пустая** база **`konspekt_v62_restore_20261029`** (другой адрес, порт или имя скрипт не

установке), встроенного PowerShell и Node.js (уже был для шага 0б).
```
powershell -ExecutionPolicy Bypass -File .\supabase\release\v62-local-pg17-check.ps1 -Dump "<папка копии>\konspekt-full.dump" -Seed ..\konspekt-v62\library-seed.sql
```
Что делает скрипт (по порядку, при любом «СТОП» дальше не идёт):
1. Проверяет копию: SHA-256 файла = записанной в `README.txt` при создании (копия цела); в конце — что файл не изменился.
2. Проверяет сервер: он сам должен ответить «127.0.0.1:55432», PostgreSQL 17, без `supabase_vault` (то есть не Supabase);
   база пустая (поверх непустой не восстанавливает, базы не удаляет). Новую пустую базу создаёт только с ключом
   `-CreateEmptyDb` и только если базы с таким именем ещё нет (`konspekt_v62_restore_20261029_2` при `-Attempt 2` и т. д.).
3. Роли Supabase (`anon`, `authenticated`, `service_role`…). Они общие для всего локального PostgreSQL, поэтому без
   разрешения скрипт их **не создаёт**: печатает список и останавливается. Разрешение — ключ `-CreateMissingRoles`
   (роли без входа, без пароля, без прав; убрать после удаления тестовой базы: `drop role <имя>`).
4. Восстанавливает копию **без объектов `supabase_vault`** (секреты Supabase; приложение их не использует — проверено в
   production 29.10). Они пропускаются по оглавлению копии, а не «прячутся» среди ошибок. Журнал `pg_restore`
   разбирается целиком (сообщения PostgreSQL переключаются на английский); каждая ошибка печатается с командой.
   Допустима **одна** известная ошибка: `ALTER EVENT TRIGGER <триггер Supabase> OWNER TO supabase_admin` — владельцем
   событийного триггера может быть только суперпользователь; в Supabase `supabase_admin` — суперпользователь, локально — нет.
   Триггер при этом создан и включён, владелец — `postgres`. Скрипт пишет это как «ОГРАНИЧЕНИЕ ЛОКАЛЬНОЙ КОПИИ»;
   `supabase_admin` суперпользователем не делается. На v62 не влияет: миграция событийные триггеры не создаёт и не
   меняет, функция триггера выполняется одинаково при любом владельце. Любая другая ошибка или непонятная строка — FAIL.
5. Сверяет восстановление: структура приложения = production **объект в объект** (`v62-prod-structure.tsv`, 145 объектов:
   функции, таблицы, представления, владельцы, права, RLS, политики, событийные триггеры). Пустые права (NULL)
   сравниваются как права владельца по умолчанию (`acldefault`): `pg_dump` не сохраняет явную запись «только владелец»,
   и после копии там NULL — те же права (из-за этого первая репетиция показала 28 «отличий» в private/analytics).
   и число строк **каждой** таблицы = в копии. Если хоть что-то не совпало — «ВОССТАНОВЛЕНИЕ НЕПОЛНОЕ»: это не полноценная
   проверка, миграцию скрипт не запускает.
6. Проходит выпуск: снимок → миграция → снимок (данные не изменились) → 77 параграфов с контрольными суммами → доступ по
   статусам → повтор миграции (отклонён) и текстов (без дублей) → откат (функции и данные как до миграции).

Ожидаемый конец: **«РЕПЕТИЦИЯ v62 НА КОПИИ PRODUCTION ПРОЙДЕНА»**. Прислать Claude файл `report.txt` из папки проверки
(в нём нет паролей, текстов и данных учеников); остальные файлы папки не пересылать. Если восстановление сорвалось и база

## Ежедневная работа

- **🎁 Подарить доступ** (подарок, повторное тестирование, особое предложение) → панель → «🎁 Подарить доступ» (на главной
  или в карточке ученика) → ID, количество дней (по умолчанию 7), количество генераций ИИ (по умолчанию 1) → «Продолжить» →
  подтверждение «Вы собираетесь подарить ученику …: 🎁 Доступ, 🤖 Генерации ИИ, 💰 Стоимость для ученика: бесплатно» →
  «Подтвердить подарок» → «🎁 Подарок выдан» с датой окончания.
  - Подарок даёт историю, физику и ИИ по фото на выбранный срок; у ученика — «🎁 Подарок до …». Это **не Premium**:
    в статистике подписок не считается, пробный период не меняет и заново не запускает.
  - Повторный подарок **добавляется** к текущему: дни — к сроку, генерации — к лимиту (использованное не теряется).
  - Если у ученика идёт Premium, подарок начнётся **после** Premium; Premium не сокращается и не меняется.
    Premium, купленный во время подарка («Продлить»), начнётся после подарка — оплаченные дни не теряются.
  - Владельцу и двум старым аккаунтам с особым ручным доступом подарок не выдаётся (их доступ не меняется).
  - Бюджет: подарок выдаётся, только если свободного бюджета (за вычетом уже обещанных подарков) хватает на
    генерации × 1,5. Подарочные генерации **не в резерве**: когда свободно только то, что зарезервировано под Premium,
    подарочные запуски ставятся на паузу, как пробные — оплаченные идут первыми. Бюджет сам не увеличивается.
  - «Отозвать доступ» отзывает и подарки. Все подарки — в «Истории» («🎁 Подарок»).

- **Ученик заплатил 299 ₽** → панель → ученик → «Выдать Premium» → Продолжить → «Подтвердить выдачу». Ничего вводить не нужно.
- **Продление** → «Продлить» → Premium. Досрочное продление начинается с конца текущего срока; неиспользованные генерации не переносятся.
- **Особые условия** (скидка, другой срок) → «Нестандартные» → срок и генерации → подтверждение с предупреждением.
  Такие выдачи записываются без тарифа (в карточке не «Premium»).
- **Бюджет** → «ИИ»: жёлтое «мало» — свободно меньше 20 % бюджета; красное «только резерв» — пробные и твои запуски на паузе,
  ученики с Premium работают. Увеличь бюджет кнопкой «Изменить бюджет».

## Откат (только по решению владельца, после резервной копии)

Главное: **после публикации сайта v62 старого каталога с текстами на сайте нет.** Сайт v61.3 снова выложил бы тексты
всем (через `js/library-catalog.js`). Поэтому сначала — меры без отката, полный откат — только в крайнем случае.

| Когда | Что случилось | Что делать |
|---|---|---|
| До публикации сайта | что угодно после шагов 2–3 | SQL Editor → весь файл `supabase/release/rollback-v62.sql` → Run (одним запросом) — база снова v61.3; старый сайт работает как раньше; тексты закрытой таблицы удаляются вместе с ней |
| После публикации | конспект не открывается, «пока недоступен» | откат не нужен: повторить шаг 3 (повторяемый) |
| После публикации | пробные генерации на паузе («приостановлено») из-за резерва | откат не нужен: увеличить бюджет в панели; при необходимости ослабить резерв: `update private.access_settings set budget_reserve_factor = 1.0, owner_reserve_starts = 0;` (только по твоему решению) |
| После публикации | не работает панель (выдача/продление) | откат не нужен: выдать через SQL Editor `select private.admin_grant('KN-…', 'premium');` / `private.admin_extend(…)` — они не менялись |
| После публикации | сбой генераций у всех | остановить ИИ: `supabase/release/ai-stop.sql` (как раньше); библиотека и личные конспекты продолжают работать |
| Крайний случай | нужно вернуть v61.3 целиком | **1)** revert merge v62 в `main` (сайт v61.3 — тексты снова публичны, решение владельца); **2)** дождаться публикации Pages; **3)** `rollback-v62.sql`. Обратный порядок на время между шагами оставит сайт v62 без библиотеки («Не удалось загрузить»), личные конспекты при этом работают |

`rollback-v62.sql`: возвращает функции v61.3 (проверено на копии production: тексты функций, права и `search_path`
совпадают с v61.3 до миграции), удаляет таблицу текстов, выключает тариф premium (выдачи остаются), бюджет не меняет;
ученики, конспекты, выдачи, генерации и журнал не меняются. Закрытые права TRUNCATE/REFERENCES/TRIGGER не возвращает.
Выданные подарки после отката остаются обычными сроками доступа до своей даты (функция подарка удаляется, пометка gift
остаётся выключенной).
Повторный выпуск после отката — снова шаги 2–3.

Последнее средство — восстановление из копии шага 0 (проверено на тестовой базе): одна таблица —
`pg_restore --data-only -t <таблица> -d DB konspekt-data.dump` в очищенную таблицу; вся база — в новый проект.
